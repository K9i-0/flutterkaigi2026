# そば屋ハザード：3Dアセット制作方針

調査日: 2026-09-05。段階: 調査・提案。画像生成、Tripo API送信、モデル制作、ゲーム実装は未実施。

## 推奨判断

Imagegenで外見を設計し、Tripo P2.0で難しい有機形状の原型を作り、Blenderでゲーム用に仕上げる。寸法・接続・可動部が重要なモデルは、CodexがBlender Pythonで生成する。どちらも同じGLB納品仕様へ揃える。

「GPT-6 Astraだけで十分なモデルを作れる」という一般的な品質保証は今回確認していない。以下は形状の性質に基づく制作判断であり、実物比較で採否を決める。API料金だけでなく、本人らしさ、修正時間、変形品質、ゲーム内の描画負荷を評価する。

| 素材 | 第一候補 | 判断理由・補完方法 |
| --- | --- | --- |
| 福ちゃん | Imagegen → P2.0 → Blender | 顔・人体・服の立体感へ生成を使う。顔の同一性は別途厳しく検査し、必要なら顔メッシュ・UVを修正する。Tripoでも本人再現は保証されない |
| そば屋 | 人体・衣装はP2.0、仮面はコード造形を比較 | 筋肉質な体格に生成を使い、白仮面の輪郭・模様は制御しやすい別パーツにする。敵ごとに生成し直さず原型を共有 |
| たこさん | Blender Pythonによる曲面造形＋専用リグから試す | フード、白い顔、丸い手、下半身の触手を分けて設計できる。布の造形が不足する場合だけP2.0を補助に使う |
| やめ太郎 | コード造形を試し、顔・髪の再現不足ならP2.0 | デフォルメ体格と丸メガネを制御しやすい。頭部は単純形状だけでは似ない可能性がある |
| 壁・床・屋根・階段・扉・窓・柵 | Blender Python | 寸法、厚み、接続、蝶番ピボット、UV、LOD、当たり判定を一緒に設計できる |
| 樽・木箱・棚・机・椅子・鐘・鍵・弾薬箱・銃 | Blender Python | 回転体、押し出し、面取りなどから作り、近接用の細部と材質を追加する |
| 特徴的な彫像・複雑な怪物・装飾 | P2.0候補 | 手作業の造形コストと見栄えへの寄与が大きいものに限定 |
| 石・木・草・瓦礫 | パラメータ付きコード生成を基本 | 数種類の原型から変形・配置を変える。重要な古木などだけTripo候補 |

コード生成は制作時にBlenderで行い、メッシュと材質を整理したGLBへ書き出す。実行時に何千もの球や箱を別ノードで組み立てる方式にはしない。滑らかな曲面、面取り、適切な法線、ベイクした質感で非ボクセルの3D表現にする。

## Tripo P2.0で確認できたこと

公式の英語PシリーズAPIとChangelogで、P2.0 PreviewのモデルID `P2-20260801` を確認した。トップページのP1紹介や旧v2記事から設定を流用しない。[P2対応履歴](https://developers.tripo3d.ai/en/docs/changelog)

- 画像入力: `POST https://openapi.tripo3d.ai/v3/generation/image-to-model`
- 複数方向入力: `POST /v3/generation/multiview-to-model`
- `quad: true` で四角面を指定可能。`face_limit` は三角面48〜50,000、四角面48〜25,000。
- `texture`、`pbr`、`texture_quality`、形状・テクスチャのseed、UV出力を指定可能。
- PBRを有効にするとテクスチャも有効になる。形状だけ比較する場合は `texture: false` と `pbr: false` を両方指定。

以上は[画像→PシリーズAPI](https://developers.tripo3d.ai/en/docs/generation-image-to-model/p)の確認事項。四角面であることと、関節がきれいに変形することは別の合格条件とする。

マルチビューは正面必須、最低2方向。`front` / `left` / `back` / `right` キーで指定できる。全方向で同じ形・衣装・照明を維持する必要がある。[複数方向→PシリーズAPI](https://developers.tripo3d.ai/en/docs/generation-multiview-to-model/p)

### 推奨する最初の設定案

福ちゃんの正面・左右・背面をそれぞれアップロードした後に使用する設計例。実行済みリクエストではない。

```json
{
  "inputs": [
    {"front": "<front_file_token>"},
    {"left": "<left_file_token>"},
    {"back": "<back_file_token>"},
    {"right": "<right_file_token>"}
  ],
  "model": "P2-20260801",
  "quad": true,
  "face_limit": 12000,
  "texture": true,
  "pbr": true,
  "texture_quality": "detailed",
  "texture_alignment": "original_image",
  "model_seed": 260905,
  "texture_seed": 260905,
  "export_uv": true,
  "auto_size": false
}
```

12,000四角面は原型の試行値で、完成モデルの性能保証ではない。ゲーム用には三角面数・分割後の頂点数・材質数・変形品質を測る。寸法はBlenderで統一する。後処理時の向きの問題を避けるため生成段階では `export_orientation` を送らず、初回互換性確認までは `compress` も省略する。[生成APIの向きに関する注意](https://developers.tripo3d.ai/en/docs/generation-image-to-model/p)

編集用四角面の保持にはFBX/OBJ等を使う。PシリーズAPIの結果例はGLB表記のため、実タスクで返る形式と四角面保持を最初に確認する。必要ならTripoの形式変換を使うが、元の四角面がそのまま保持されるかはBlenderで検査する。GLBへの最終出力時には三角面化され、UV境界等で頂点も増える。[Tripo形式変換](https://developers.tripo3d.ai/en/docs/models-convert)、[Blender glTF仕様](https://docs.blender.org/manual/en/4.0/addons/import_export/scene_gltf2.html)

### 料金の目安

公式ChangelogではP2形状のみ100 credits、標準110、detailed 120、extreme 130。1 credit = US$0.01なので、それぞれUS$1.00 / 1.10 / 1.20 / 1.30。一般価格表の別シリーズ向け基本価格・追加料金を機械的に足さず、P2の履歴記載を見積もり基準にする。[P2価格](https://developers.tripo3d.ai/en/docs/changelog)、[換算・処理価格](https://developers.tripo3d.ai/ja/pricing)

例: 福ちゃん・そば屋を各3候補、detailedで生成すると `2 × 3 × $1.20 = $7.20`。これは3D生成部分のみ。Imagegen、変換、リグ、モーション、追加試行、税は含まない。公式価格表のオートリグは25 credits、リターゲットは1モーション10 creditsだが、実請求はタスクの `credits_consumed` と照合する。見た目が不採用でも処理自体が成功した生成は有料。[課金ライフサイクル](https://developers.tripo3d.ai/en/docs/billing)

## Imagegen入力画像の作り方

これは本作向けの制作提案。今回は生成していない。

1. 正典画像と設定から、全身の外見・衣装・素材を先に決める。
2. 正面を基準に、同一ポーズ・同一比率・同一照明の左右と背面を作る。
3. 1方向1画像。文字、寸法線、背景小物、複数人、複数方向のコラージュを3D生成入力へ混ぜない。
4. 人型はAポーズを基本に、腕と胴、左右の脚、指が重ならないようにする。たこさんは触手を交差させず、腕2本と下半身を明瞭に分離する。
5. 背景は無地、光は柔らかく均一、頭から足先まで入れ、強い遠近・映画照明・霧・被写界深度を避ける。
6. 福ちゃんは顔の確認用寄り画像も別途用意する。ただし全身用の側面スロットに顔アップを混ぜない。
7. 銃・鍵・持ち物は身体と別アセットにする。正面だけでなく、TPSで常に見える背中・肩・後頭部を優先して監査する。

複数方向で顔・体格・衣装が変わってしまう場合、矛盾した4枚を送るより、整合した正面と背面の2枚、または単画像方式を比較する。

正典参照:

- 福ちゃん: `02_CHARACTERS/Fukuchan.jpg`、`02_CHARACTERS/05_Fukuchan.md`。本人と同じ顔で識別できること。
- そば屋: `02_CHARACTERS/Sobaya.jpg`、`02_CHARACTERS/01_Sobaya.md`。白仮面、ニュートラルなグレー肌、固有の体格を維持。
- たこさん: `03_SCRIPTS/00_TEMPLATES/characters/character_takosan_basic_sheet.png`、`02_CHARACTERS/02_Takosan.md`。人間型の腕2本、丸い白い手、下半身の触手を維持。通常形の6本を初期設計に使う。
- やめ太郎: `02_CHARACTERS/Yametaro.jpg`、`02_CHARACTERS/06_Yametaro.md`。顔・頭部・丸メガネ・体格比率を維持。

## Blenderでゲーム用に仕上げる

順序は「形状修正 → UV・材質整理 → リグとウェイト → モーション → LODと書き出し」。後からメッシュを作り直したときはウェイト・UV・アニメーションを再検査する。

- 顔、肩、肘、股関節、膝、指、触手の付け根を動かし、接合・貫通・潰れを調べる。四角面でも必要な箇所は手直しする。
- 福ちゃんの頭部が似ていない場合は、テクスチャだけでごまかさず輪郭・目鼻の位置も修正。原型としての修正量が大きすぎれば再生成を比較。
- スケールはメートルへ統一。接地位置、モデルの前方、原点、装備用ソケット、扉の蝶番を統一仕様にする。
- 材質は少数へ整理し、共有できるものを共有。Blender独自の複雑なノードは基本PBRへベイクする。
- 近接人物は2K、小物は512〜1Kから試す。細かい凹凸はノーマル等へ移し、ゲーム用に8Kをそのまま持ち込まない。
- 髪は近接で形が保てる不透明な束形状を優先。大量の透過髪・半透明衣装は描画順と重なりの検証対象。
- 人型のスキニングは1頂点4影響を初期仕様にし、LODでも骨格・ソケット・クリップ名を揃える。
- 当たり判定は描画メッシュと別にする。移動はカプセル、静的建築は簡略化した形状、被弾は頭・胴・手足の簡易領域で扱う。
- `.blend`に編集可能な元データを残し、出荷GLBは法線・UV・テクスチャ・三角面数・骨・アニメーションを再検査する。

初期の造形目安（本作の試行値。Flutter Scene公式上限ではない）:

| 対象 | 近接用の三角面目安 | 留意点 |
| --- | ---: | --- |
| 福ちゃん | 20,000〜30,000 | 顔・手・肩・後頭部へ配分。1〜3材質程度から試す |
| そば屋 | 10,000〜20,000 | 群れで評価。中遠距離版と影用の簡略形状を検討 |
| たこさん・やめ太郎 | 8,000〜20,000 | 触手の曲がり、丸メガネと顔の輪郭を優先 |
| 一般アイテム | 300〜3,000 | 手持ち武器の接写版は個別判断 |

### リグとモーション

福ちゃん・そば屋・やめ太郎は二足の共通命名規則へ揃える。ただし体格ごとのウェイトとリターゲット調整は必要。Tripoのrig-checkを通し、オートリグとBlender作成の修正量を比較する。

公式英語ページでは人型向けに `v1.0-20240301`、非人型向けに `v2.5-20260210` と説明される一方、同ページ例は後者とbipedを組み合わせ、日本語ページでは異なる `rig-v2.0` 等の表記がある。リグモデルを決め打ちして大量生成せず、最初の1体でAPI対応・骨名・変形を確認する。[英語Auto Rig](https://developers.tripo3d.ai/en/docs/animations-rig)、[日本語Auto Rig](https://developers.tripo3d.ai/ja/docs/animations-rig)

たこさんは「腕2本＋触手6本」の複合構造なので、octopodへ自動的に当てはめない。Blenderで胴・両腕・6本の触手チェーンを設ける専用リグを第一候補にする。

最初のモーションは福ちゃんの待機・歩行・走行・構え・発砲・リロード・被弾、そば屋の待機・追跡・攻撃・被弾・倒れる動作。たこさんとやめ太郎には待機・移動・会話用動作を用意する。移動はゲーム側で制御し、初期はその場モーションを使う。武器操作・手の位置・接地はBlenderで調整してキーへベイクする。

Flutter SceneはglTFのアニメーション読込とクリップのブレンドに対応している。ゲーム側の攻撃判定、入力、AI、状態遷移は別に実装する。[公式Animationガイド](https://fscene.dev/guides/animation/)

## Flutter Sceneへの接続と軽量化

既存の `17_FLUTTER_SCENE_GAME` は `flutter_scene ^0.22.2`、Flutter 3.47.1を使用。`19_FLUTTER_SCENE_VRM_LAB` はVRM向けの固定forkを使用。本作の通常GLBにVRMは必須ではなく、まず公式版の機能で検証する。既存アプリの依存関係は今回変更しない。

同梱GLBはビルド時に `buildScenes` で変換し、`loadScene` で読み込む。テクスチャの圧縮とmipmapもビルド工程にまとめ、ロード中にパイプラインをwarm-upする。生成元GLBと実行用変換物を区別する。[公式Assets and loading](https://fscene.dev/guides/assets-and-loading/)

公式performanceスキルに従い、実機profileモードのDevToolsでUI時間とraster時間を測る。60fpsなら各フレームの目標は約16.7ms。対象端末は未指定なので、既存環境のmacOSで導入確認後、採用する実機の最低性能を基準に決める。debugでのUI操作検証と性能測定を混同しない。

採用する対策は、反復する静的部品のインスタンシング、区画ごとのカリング、遠景LOD、材質共有、静的な建築の影キャッシュ、必要なポスト処理だけの使用。負荷が高い側へ順に対処する。[公式performanceスキル](https://github.com/bdero/flutter_scene/blob/master/packages/flutter_scene/skills/flutter_scene-performance/SKILL.md)

実装前に把握しておく制約:

- `LodComponent` は影・depthプリパスに最高詳細を使い、ハードウェアインスタンシングとの組み合わせも未対応。木や樽は区画別・詳細度別のバッチをアプリ側で管理する案を検証する。
- `shadowStatic` は実際に動かないメッシュノードへ個別に設定する。開閉する扉、キャラクター、動く草は対象外。
- 描画範囲外のスキン付きモデルを通常のカリングだけで十分に停止できるとは仮定しない。区画単位でAI・アニメーション・表示を管理する。

これらは[公式performance詳細](https://github.com/bdero/flutter_scene/blob/master/packages/flutter_scene/skills/flutter_scene-performance/references/performance.md)とローカル0.22.2のソースで確認した。さらに `lib/src/render/instance_batching.dart` は `jointsTexture != null` のモデルを自動バッチ対象から除外している。同じそば屋GLBを共有しても、各個体のスキン描画が1drawへまとまるとは限らない。

本作での応用提案:

- 最初は同時に動くそば屋4〜6体。その後8体・12体へ増やし、UI/rasterのp95、カクつき、メモリを比較する。
- 近距離の敵だけ詳細な骨格・影を使い、中遠距離や別部屋では更新頻度・表示・影を調整する。簡略モデルへの切り替えは共通骨格で検証する。
- キャラクターと開閉物の影だけを動的にし、静的建築をキャッシュする。必要なら敵の影を簡略形状へ置換する。
- 雰囲気は材質、環境光、霧、局所光、色調整から作る。SSR・DoF・多数の影付きライトを一度に有効化しない。
- 重い場合は遠景・影・全画面効果を先に調整し、福ちゃんの顔と近接での識別性を保つ。解像度は最後に実測で調整する。

## マップとゲーム内容の案

ユーザー指定の確定部分は「三人称の福ちゃんを操作し、そば屋と戦いながら探索」「たこさん、やめ太郎も登場」「マップとアイテムも作り込む」。以下は提案であり、新たな固定設定ではない。

既存 `03_SCRIPTS/49_sobaya_hazard_trailer/script.md` の寒村・鐘楼・古城を参考に、最初の完成区画を「村入口 → 広場 → 民家 → 倉庫 → 鍵で開く鐘楼」とする。民家と裏路地をつないで、戻り道・遮蔽物・迂回経路を作る。やめ太郎は鍵と手掛かりの提供、たこさんは救援・同行役を初期案にする。

建築は実寸のモジュールで組み、地面・石壁・木材のテクスチャ密度を揃える。梁、窓枠、雨樋、建具、調理道具、棚の内容物、汚れで場所の用途を表現する。マップ全体を1つの画像から一体生成する方式は、通路幅、内部空間、衝突、扉の可動、見えない区画の除外が難しくなるため第一候補にしない。

アイテムは最初に拳銃、弾薬箱、回復品、鍵、調査文書、壊せる木箱を用意。見た目とは別にID・取得・使用・残数・保存状態を定義する。武器の手持ちソケット、箱の破壊前後、鍵と扉の対応まで作る。看板や文書の正確な文字は画像生成任せにせず、後からテクスチャへ組む。

ゲーム基盤には肩越しカメラと壁衝突、移動カプセル、照準と射線、敵の追跡・攻撃、被弾判定、拾得、インベントリ、扉、保存を含める。視覚モデルだけではゲームにならないため、最初の区画で一連の遊びを成立させてから面積を広げる。

## 最初に比較する試作と合格条件

1. **造形比較**: 福ちゃんをP2.0で1体、たこさんと木製扉・樽をBlender Pythonで制作。同じ照明の正面・側面・背面・TPS距離で見比べる。顔、曲面、触手、質感、修正時間を記録。
2. **可動比較**: 福ちゃんの歩行・構え・リロード、たこさんの腕と触手、扉の開閉を確認。四角面の外観だけで合格にしない。
3. **敵負荷試験**: 採用手順でそば屋を作り、4・8・12体で同じ追跡・戦闘シナリオを実行。共有アセット、影、更新頻度の効果を測る。
4. **完成区画**: 4キャラクター、探索ループ、鍵扉、アイテム、戦闘を村1区画に統合。マップを拡張する前に実機で確認。

合格条件は、正典の同一性、TPS背面の品質、関節変形、装備の位置、足滑り、衝突とカメラ、実機フレーム時間、再ロード時の状態復元。Tripoが勝つ部位だけ生成へ寄せ、コード造形が通った部位はそのまま採用する。

将来の正本置き場は `04_GAME_ASSETS/3d/` を候補とし、入力画像・生成設定・task ID・取得原型・Blender元データ・制作スクリプト・ゲーム用GLB・LOD・衝突定義を関連付ける。ゲームからは相対symlinkで参照し、候補やビルド済み派生物を無条件にGitへ追加しない。具体的な保存方針は実制作時に既存のGit管理方針と整合させる。
