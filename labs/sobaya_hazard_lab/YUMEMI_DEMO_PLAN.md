# ゆめみ村体験版 — 制作仕様

2026-09-13。ユーザーとの世界観検討を本版の正本とする。従来の脱出編より優先。

## 体験版の到達点

港から着任した福ちゃんが村の異変を調べ、神社の巨大そば屋を撃破する。巨大そば屋の片言からアクシデンチュアの関与を知り、神社の近くの施設を発見して終了する。帰還しない。エンジンの仕組みとクローンの正体は中盤以降の情報として留保する。

## 三つの区画

1. ゆめみ港（内部ID village）：桟橋、歓迎看板、漁具倉庫と荷揚げ場。船は福ちゃんを置いて去る。やめ太郎が基本操作を案内し、「そば屋がビールを置くため祠を壊したのだろう」と呑気に推測する。
2. 村の生活圏（内部ID farm）：空き店舗、住宅、旧役場と社宅。たこさんが空き店舗で営業し、商店が解禁される。探索して参道の情報と鍵を持ち帰り、山への門を開く。救助準備やエンジンの説明はしない。
3. 山の神社（内部ID mountain）：森の参道、鳥居、境内。巨大そば屋を撃破したら、通常敵の全滅や二人への報告を要求せず、裏手の施設看板を調べて終了する。会社名の看板は港から見せない。

## 情報の順序

- 企業依存、撤退、過疎化、左遷は村の生活史として序盤から示す。事件の原因まで会社だとは断定しない。
- 通常そば屋は「ビール」の単語と非言語音だけ。ボスは「カイシャ」「ビール」「くれない」「よこせ」と片言をつなぎ、会社名を口にする。本人は普通に会話できる。キャラクターの外見同一性は維持する。
- 神社が原因というのはやめ太郎の推測。祠に異常は見つからず、隣接施設とボスの発言がつながる。
- 収集文書、ポスター裏書き、会話選択肢、タイトル、クリア画面も同じ情報制限にする。

## 制作・検証

### 今後の改善手順：Flutter Sceneでの反復制作（2026-09-14採用）

ユーザー指定により、[Building games with Astra](https://developers.openai.com/blog/how-to-build-games-with-astra)の体験・目標画・再現検証を中心にした制作手順を採用する。プラットフォーム固有部分は現在のFlutter Scene構成に合わせる。

| 記事側の手段 | 本作で使う手段 |
| --- | --- |
| TypeScript / Vite、Three.js / WebGPU / TSL | Dart / Flutter、同梱のFlutter Sceneと既存の材質・照明・描画パス。変更前に使用版の実装と対応機能を確認する |
| JavaScriptの状態公開インターフェース | 本編の `madogiwa.inspectHazardGame`、端末側の `madogiwa.deviceDiagnostics` |
| Playwrightの再現シーンとブラウザ操作 | Dart MCPで本編をdebug起動し、Marionetteの `madogiwa.openGameScenario`、UI操作、スクリーンショットで検証 |
| Vitestとjourney tests | 既存のDart / Flutterテストと `madogiwa.auditCampaign`。直接配置による場面検査と、通常操作経路を通る検査を分ける |
| ブラウザのフレーム間隔・描画カウンター | 本編profileベンチマーク、UI / Raster時間、Scene描画呼出回数、端末診断。必要に応じてMetal / InstrumentsでGPU待ちを確認 |
| Web Workersによる生成処理の分離 | まず既存のオフラインGLB生成と区画ロードを利用。実行時CPU処理が原因と確認された場合にDart isolateや処理分割を検討する |
| Sitesによるブラウザ配布 | 既存のFlutterネイティブビルド・配布手順 |

本編の入口は `lib/game_main.dart`。検証室の `inspectHazard` / `openScenario` と本編のextensionを混同しない。呼び出しと接続は [MCP_DEBUGGING.md](MCP_DEBUGGING.md)、性能条件は [GRAPHICS.md](GRAPHICS.md)を正本とする。Scene.renderの呼出回数はdraw callsや実提示FPSを意味しない。取得できない描画指標は未計測として扱う。

最初の改善単位は生活圏の「商店を出る→そば屋を見つける→ビールで誘導→建物裏を抜ける」という短い経路とする。既存配置と進行を確認して経路を選び、以下を一巡させてから港・神社へ展開する。

1. 現行画面・カメラ・開始状態・設定を保存し、道、敵の輪郭、暗部の顔、遮蔽物の見え方を評価する。既存コンセプトを参照し、不足する場面だけプレイ視点の目標画を用意する。
2. 同じ経路で、投擲の着地点・音源・敵の調査先、発見・捜索・帰還、効果音とBGMの変化を記録する。足りない診断だけ追加する。
3. 観測した問題に絞って美術・挙動を変更する。描画と判定が参照する位置・時間をそろえ、同じカメラの画面と通常操作の両方で再確認する。
4. 性能変更は同じ端末・画質・解像度・電源条件で変更前後を比較する。iPhoneの発熱は非充電の連続試遊で別途確認し、Macやdebugの結果から推定しない。
5. 採用変更、検証条件、結果、未確認事項を軽量な `qa/` 記録へ残す。目標画への近さと操作感の判断は、状態テストの合否とは別に記録する。

## 実装・検証結果

全459テスト通過（任意1件スキップ）、静的解析指摘0。終幕ナレーションの読み修正後、関連18テストも通過。採用音声98件のファイル整合検査と口形エンベロープを更新。

Dart MCPでMac debugを起動し、Marionetteによる実描画の自動走行で港→商店→神社→施設発見を完走。会社名の発言と終幕の再生後、`clear`画面への到達と音声エラー0を確認した。自動照準による検査であり、人間の難易度評価や実時間FPS測定ではない。

3背景の合計GLB容量は39,265,864→34,715,532 bytes。静的三角形数は55,535→55,363。日本的な屋根・看板・鳥居・港を追加しながら従来の規模を維持。描画性能や発熱の改善率を意味しない。
